# Releasing

For maintainers. Every release ships both binaries, `ascend-tunnel` and `ascend-agent`, signed the same way,
from `.github/workflows/release.yml` and `.goreleaser.yaml`.

## Steps

A release candidate first, then the release, both from the same commit on `main`:

1. Tag `vX.Y.Z-rc.1`. It publishes a GitHub pre-release (never "Latest") and the image `X.Y.Z-rc.1`, and
   leaves Homebrew alone. Check a macOS binary from it:
   `codesign -vvvv -R="notarized" --check-notarization ascend-tunnel` says the requirement is satisfied.
   Something wrong: fix it on `main` and tag `-rc.2`.
2. Tag `vX.Y.Z` on the same commit. It publishes the release ("Latest"), the images `X.Y.Z` and `X.Y`, and the
   Homebrew casks.

A published release never changes and a tag never moves, so a fix after the release is the next patch version.

## Who can release

Anyone with write access can push a `v*` tag on a commit on `main`; nobody can move or delete one. The run then
waits until a code owner other than the tag's author approves it (no admin bypass). Only then does
`release.yml` build on a macOS runner and read its credentials from the `release` environment, which only `v*`
tags may use.

The tagged commit's own `release.yml` is what runs, so the approver checks that the tag points at a commit on
`main` (the approval screen shows it, or `git branch -r --contains <sha>` lists `origin/main`).

## Credentials

In the `release` environment, never as repository secrets (which any branch's workflow could read):

| | Kind | What |
|---|---|---|
| `MACOS_APP_P12`, `MACOS_APP_P12_PASSWORD` | secret | Straiker's Developer ID Application certificate, base64 `.p12`, and its password |
| `APPLE_APP_PASSWORD` | secret | app-specific password of `APPLE_ID`, for `notarytool` |
| `APPLE_ID` | secret | the Apple ID that notarizes (a secret so the public run logs mask it) |
| `APPLE_TEAM_ID` | variable | Straiker's Apple team id (public: it is in every signed binary) |
| `JSIGN_*` | secret | Windows Authenticode through a cloud HSM (`scripts/sign-windows.sh`); optional |
| `TAP_APP_CLIENT_ID` | variable | client ID of the tap-publisher GitHub App, installed on straiker-ai/homebrew-tap only with Contents: read and write |
| `TAP_APP_PRIVATE_KEY` | secret | that App's private key. The job mints a token for homebrew-tap only, to publish the casks after the release. Required on a release tag; prerelease tags never touch the tap |

A tag fails if macOS signing or notarization is missing, rather than publishing binaries Gatekeeper would
block. Windows signing stays optional until Straiker has an OV code-signing certificate in a cloud HSM.

## Package managers

- **Homebrew:** the casks are generated by GoReleaser and pushed to
  [straiker-ai/homebrew-tap](https://github.com/straiker-ai/homebrew-tap) only once the release is published
  (`scripts/publish-casks.sh`). Nobody edits the tap by hand; change `.goreleaser.yaml` instead.
- **winget and Scoop:** the manifests are generated but not published yet: their repositories don't exist.
- **deb/rpm:** built with the release and attached to it; they install a systemd service.
